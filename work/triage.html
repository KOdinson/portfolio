Triage: thirteen alerts, five decisions

Security monitoring tools produce one row per alert. An attack produces many alerts. The analyst is left to notice that rows 3, 9, 14 and 22 are the same incident. This concept does that noticing for them and says how it did it.

The prototype

Where this comes from

My degree and certifications are in security: an A.A.S. in Cyber Security, Security+, CySA+ and PenTest+. Alert monitoring was part of that training. I learned triage in a classroom and a lab, not on a night shift, and this project is labelled a concept for that reason.

What the training makes clear is the shape of the problem. Detection rules fire on single events. People attack in sequences. A flat list sorted by time or severity scatters one sequence across the screen and mixes it with routine noise.

The problem statement comes from coursework and published guidance on alert fatigue, not from interviews. I have not observed working analysts for this project.

Key decisions

The unit of work is a case

Alerts that share a machine or an account become one row. Thirteen alerts become five cases. The header states both numbers, so the analyst can see how much the grouping is doing and is never left wondering where alerts went.

Grouping has to explain itself

Every case opens with "Why these are together" in one or two sentences. If the tool merged things that do not belong together, the analyst can see the reasoning and reject it. A grouping with no stated reason is one more thing to distrust.

You can turn it off

One switch returns the flat list. In that mode, an alert with relatives elsewhere says so: "3 other alerts on FIN-LT-014 sit elsewhere in this list." The switch is there for trust, and it also makes the argument for grouping better than any description could.

Events in the order they happened

Inside a case, alerts run as a timeline. The laptop case reads top to bottom as a story: a document opened a shell, the shell downloaded a file, the machine called out, a task was scheduled. The order is the evidence.

Closing costs one keystroke more

Closing a case asks why it is safe, with four answers on keys 1 to 4. Nearly as fast as closing blind, and the reason is saved. "Test or scan" on the scanner case is the data someone needs later to fix the rule that keeps firing.

Hands stay on the keyboard

J and K move through the queue, E escalates, A assigns, C closes. Every shortcut is printed on its button, so the keys are learned by using the mouse and then no longer needing it.

Severity is a shape and a word before it is a colour: a triangle for high, a diamond for medium, a circle for low. Rule names are written as plain sentences, such as "Office document launched PowerShell", with the raw detail one line below.

Limits and next steps

The grouping here is the simplest possible rule: same machine or same account. Real incidents cross machines and accounts, and a real product would need far better correlation. The interface question stands either way: however alerts are grouped, the grouping needs a stated reason and an off switch.

  • Interview five working analysts about the last incident they caught late, and what the queue looked like at the time.
  • Timed comparison: the same thirteen alerts flat and grouped, measuring time to identify the two real incidents.
  • Test a wrong grouping on purpose. Do analysts read the reason and catch it, or trust the tool?
  • Design the case that spans two machines, where the simple rule fails.
