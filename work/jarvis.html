JARVIS: an assistant that asks before it acts

I built a voice and text assistant for my own desktop. It can search the web, remember things about me, read files, write files and run commands. The last two are where the design work was: how much should software be allowed to do on your behalf before it has to stop and ask?

Role
Sole designer and builder
Scope
Conversation window, voice input, permission flow
When
June to July 2026
Status
Working app. One user so far: me.

The two windows

The design problem

An assistant that only talks is safe and limited. An assistant that can act is useful and dangerous. The model decides what command to run, and models are sometimes wrong. I wanted the usefulness without ever being surprised by something it did.

I split its abilities into three groups and gave each a different rule.

Free
Look, search, rememberReading a file, listing a folder, searching the web, saving a note about me. These happen without asking, because none of them changes anything.
Ask first
Write a file, run a commandEvery one of these stops and shows a confirmation dialog. Nothing happens until I answer.
Never
Certain foldersA short list of folders holding sensitive project files is walled off completely. The assistant cannot read, list or search inside them, and there is no dialog that would let it.

Key decisions

Show the exact action

The dialog prints the literal command or the full file path in a monospace box, in a different colour from everything else. It does not show the assistant's summary of what it plans to do. A summary can be wrong in a way the real command cannot.

Every exit means no

Closing the dialog with the window's X counts as Deny. Not answering for three minutes counts as Deny. If the app starts without its dialog attached, every write and command is refused outright. There is no path where silence becomes permission.

The dialog blocks

The confirmation is modal and sits on top of the conversation. Interface guidelines usually say to avoid that. Here it is right: the assistant is paused mid-action and waiting, and the screen should say so.

Say where your words go

A button in the header switches between an online model and one that runs on my own machine. Switching posts a line in the conversation in plain terms: "private/offline" or "smart/online", and that the context was cleared.

Voice goes through the text box

Push-to-talk transcribes what I said into the same entry field, then sends it. I see what it heard before I see the reply, so a mishearing is obvious and does not turn into a confusing answer.

Three voices in the transcript

My lines, the assistant's lines and system notices each have their own colour, and system notices are smaller and italic. An error from the microphone never reads as something the assistant said.

Critique of v1

  • Every request looks equally serious. Creating a text file and deleting a folder get the same dialog. After enough harmless approvals, the hand learns to click Allow. Risk should change the dialog: a plain one for creating, a slower one with the consequence spelled out for deleting or overwriting.
  • Allow and Deny are twins. Same size, same weight, side by side, with Allow first. The safe choice should be the easy one to hit.
  • The raw command is honest but not enough. I can read PowerShell. Most people cannot. The dialog needs one plain sentence above the command saying what it will change, with the command kept below as proof.
  • The brain switch warns after the fact. It clears the conversation and then tells you. It should say so on the button or ask first.
  • Listening has no shape. Push-to-talk records for a fixed six seconds and the only sign is the word "Listening..." in small grey text. It needs a visible countdown and a way to stop early.
  • The transcript depends on colour. The name prefixes help, but blue and green on dark navy are close for some readers.

One user, no testing with anyone else. That is fine for a personal tool and not enough to claim the permission flow works for other people. The study I would run: give five people a list of ten requests, two of them quietly destructive, and count how many destructive ones get approved.
